# Weather Risk Intelligence Agent: submission summary

**Repository:** https://github.com/contactTAM/weather-risk-agent · **Live demo:** https://weather-risk-agent-ae3s.onrender.com (the access code is in the submission email) · **Run locally:** README "Quick start"

**What it does.** A chat agent that ranks, compares and explains how exposed 14 US distribution hubs are to weather disruption. E.g. "Which Midwest hubs are most exposed to winter disruption?" or "Why is Dallas high?", with follow-ups that keep their context. Every answer carries a hub/score table, the reasoning, the data sources and periods, the assumptions and an uncertainty level.

**Approach: numbers from code, words from the model.** Public data (Open-Meteo daily reanalysis for the last 5 full years, OpenFEMA county declarations for the last 20, live NWS alerts) is cached and scored by deterministic, unit-tested Python. Claude (`claude-sonnet-5-5`, set via `LLM_MODEL`) only chooses among six typed tools and explains the results. Its answer is constrained by a JSON schema at the API and re-validated with Pydantic (one retry). The model returns hub IDs only, and the code fills in the scores. A grounding check flags any number in the answer that no tool returned.

**Scoring logic (the KPI).** Four hazard scores (winter, hurricane/wind, flood/heavy rain, heat), each 0–100, combine into a composite **Weather Disruption Risk Score** (weights 0.30/0.25/0.30/0.15). Indicators are yearly averages of threshold days (e.g. snow ≥ 1 cm, gusts ≥ 60 km/h, rain ≥ 25 mm, ≥ 35 °C) plus FEMA declaration counts. They're scaled against **fixed, documented anchors**, not min-max across hubs, so a hub's score doesn't depend on the others and changes over time mean something. Every score returns its full breakdown. Levels: low < 33 ≤ moderate < 66 ≤ high. Hubs within 3 points of each other are flagged as close calls.

**Architecture (brief).** FastAPI serves the chat UI (with browser voice) and the API. Storage is split in two: a SQLite data cache, rebuildable from a 0.5 MB seed, and Neon Postgres for state that must survive restarts on the free tier (score snapshots, the alert log, chat memory). Bonus: alerts run as **refresh, then compare** every 6 h from GitHub Actions, because the free instance sleeps. A freshness guard blocks comparisons on stale data, and alerts go to a webhook or Slack.

**Quality.** 71 unit tests (no network or LLM). The 19-case evaluation set uses deterministic checks with **expected values computed from the scoring code at run time**. They include false premises, unknown hubs, out-of-window years, Hebrew, prompt injection and multi-turn changes. Result: 19/19 locally and 19/19 against the live deploy. **How it was built:** plans first (approved in plan mode), one verified commit per milestone, and changes driven by real data (docs/ARCHITECTURE.md §14). The full Claude Code session is part of the submission.

**Key assumptions.** The hubs are fictional (real cities; the city centre stands in for the site). "Last year" means the last full calendar year (now 2025). "Had snowfall" means ≥ 0.1 cm; the winter score uses ≥ 1 cm days. FEMA declarations reflect impact and process, not weather alone.

**Limitations.** Reanalysis smooths extremes and under-counts peak gusts, so the hurricane signal relies on FEMA. Five years is short for rare events. The weights are judgment calls, not fitted to real disruptions, and the score measures *exposure*, not vulnerability or business value. The agent states these. Next steps: fit the weights to disruption data, and add hub vulnerability, station data and forecast alerts.
