# Weather Risk Intelligence Agent: submission summary

**Repository:** https://github.com/contactTAM/weather-risk-agent · **Live demo:** https://weather-risk-agent-ae3s.onrender.com (the access code is in the submission email) · **Run locally:** see README "Quick start" (about 2 minutes, Anthropic key required)

**What it does.** A chat agent for logistics analysts that ranks, compares and explains how exposed 14 US distribution hubs are to weather disruption. It answers questions like "Which Midwest hubs are most exposed to winter disruption?", "Compare Miami and Houston on hurricane and flood", "What % of days in Denver last year had snowfall?" (10.1% in 2025) and "Why is Dallas high?". Follow-ups such as "and Chicago?" keep their context. Each answer comes with a hub/score table, the reasoning, the data sources and periods, the assumptions, and an uncertainty level.

**Approach: numbers from code, words from the model.** Public data (Open-Meteo daily reanalysis 2021–2025, OpenFEMA county disaster declarations 2006–2025, live NWS alerts) is cached in SQLite and scored by deterministic, unit-tested Python. Claude (`LLM_MODEL`, verified with `claude-sonnet-5-5`) only chooses among six typed tools and explains what they return. Its final answer is constrained by a JSON schema at the API level and re-validated with Pydantic, with one retry on failure. The model returns hub IDs only, and the code fills in the scores. A grounding check flags any number in the answer that didn't come from a tool.

**Scoring logic (the KPI).** Four hazard scores (winter, hurricane/wind, flood/heavy rain, heat), each 0–100, combine into a composite **Weather Disruption Risk Score** (weights 0.30/0.25/0.30/0.15). Indicators are yearly averages of threshold days, such as snow days ≥ 1 cm, gust days ≥ 60 km/h, rain days ≥ 25 mm and days ≥ 35 °C, plus FEMA declaration counts. Each indicator is scaled against **fixed, documented anchors**, not min-max across hubs, so a hub's score doesn't depend on the other hubs and score changes over time are meaningful. Every score returns its full breakdown: raw value, normalized value, weight and points contributed. Levels: low < 33 ≤ moderate < 66 ≤ high. Close calls (within 3 points) are flagged as uncertain.

**Architecture (brief).** FastAPI serves a single-page chat UI (with browser voice input and output) and the endpoints `/chat`, `/scores`, `/hubs/{id}/breakdown`, `/refresh`, `/alerts/check` and `/health`. The agent runs a manual Claude tool loop with session memory in SQLite. Bonus: an APScheduler job (and an endpoint) diffs scores against the last snapshot, watches for new Severe/Extreme NWS alerts and POSTs JSON to a webhook. In the demo it caught a real NWS Freeze Warning at Atlanta. Why SQLite: one file, no ops, an offline demo, and a 0.5 MB data seed so a fresh clone works immediately; at scale it would move to Postgres.

**Quality.** 47 unit tests (no network or LLM; HTTP mocked; fake LLM client for the agent loop, the retry and refusal paths, and memory). The evaluation set has 14 cases with deterministic checks, and **the expected values are computed from the scoring code at run time**: correct tools, hub order, numbers within tolerance, premise checks, unknown hub, out of scope, no ungrounded numbers. Result: 14/14 locally and 14/14 against the live deploy (`evals/sample_results*.json`).

**Key assumptions.** The hubs are fictional (real cities, with city-centre coordinates as the hub site). "Last year" means 2025. "Had snowfall" means ≥ 0.1 cm, while the winter score uses ≥ 1 cm days. FEMA declarations reflect impact and process, not weather alone.

**Limitations.** Reanalysis grid data smooths extremes: peak gusts are under-counted, so the hurricane signal relies on FEMA. Five years is a short window for rare events. The weights are documented judgment calls, not fitted to real disruption outcomes. The score measures *exposure*, not hub vulnerability or business value. All of these are stated in the agent's answers. Next steps: fit the weights to disruption data, add hub vulnerability and criticality, add station data and NOAA Storm Events, and add forecast-driven alerts.

**How it was built.** Plan first (plan mode, approved), then 11 milestones with one commit each, each verified before the next. Real data and API behavior drove three documented changes: anchor calibration, FEMA county-only rows, and JSON-schema output replacing a forced tool call.
